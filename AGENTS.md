# Productivist — Agent Instructions

## Commands

```
npm install
npm run dev       # ng serve (Angular CLI dev server, http://localhost:4200)
npm run build     # ng build (production, esbuild-based application builder)
npm run watch     # ng build --watch --configuration development
npm run check:lazy # ng build --stats-json + scripts/check-lazy-chunks.mjs: fails if a presentation (or Flow-only code) leaks into the initial bundle
```

No test framework, no linter, no formatter configured.

## Thunderbird add-on

The built app also runs as a Thunderbird add-on (a WebExtension that opens `app/index.html` in a tab).

```
npm run build:tb   # production + `thunderbird` configuration, then assembles dist/thunderbird and dist/productivist.xpi
npm run tb:lint    # web-ext lint
npm run tb:run     # launches Thunderbird with the add-on loaded (needs Thunderbird installed)
```

- `extension/` holds `manifest.json` and `background.js`; `scripts/package-thunderbird.mjs` copies them next to the Angular build and syncs the manifest version with `package.json`.
- Extension pages run under a strict CSP: no inline `<script>`, no inline event handlers, no remote scripts. Keep `index.html` free of them (the theme pre-paint snippet lives in `public/theme-init.js`, the Cookie font is bundled from `src/fonts/`), and keep `inlineCritical: false` in the `thunderbird` build configuration.
- Manual install: Thunderbird → Tools → Developer Tools → Debug Add-ons → Load Temporary Add-on → pick `dist/thunderbird/manifest.json`.

## Backend

`backend/` is a separate Spring Boot 4 / Java 21 / Postgres sync service (Maven, plain `JdbcClient`, Flyway). The Angular app stays local-first; see `backend/README.md` for run instructions and the API. It is not part of the npm scripts.

The frontend side is optional and controlled by `syncEnabled` in `src/environments/environment*.ts` (false hides the account UI and disables sync). In production the app calls `/api/*` on its own origin: the root `Dockerfile` serves the build with nginx (`deploy/nginx.conf.template`), which proxies `/api/` to the backend's private Railway address and rate-limits it, so the backend has no public domain. The Thunderbird add-on is not served from that origin, so `npm run build:tb` takes `API_URL=https://<frontend-domain>` (written to the git-ignored `environment.thunderbird.ts` by `scripts/write-thunderbird-environment.mjs`; unset means sync disabled). `AccountService` holds the email + password login/signup; the header's `login-popover` is the entry point and the account block lives in the global Configuration modal (`config-modal`: language, theme, account; `account-settings` is its account block), opened from the menu's Configuration entry or the header chip through `ViewService.openConfiguration()`; `SyncService` (instantiated in `AppComponent`) diffs the todos/projects/milestones signals against per-row metadata in `productivist.sync` to find edits and deletions, so the stores themselves know nothing about syncing — the pure logic is in `src/lib/sync-engine.ts`. Settings, daily plan and multitask state travel as one blob (`buildState`/`applyState` in `sync.service.ts`); a new persisted setting only syncs if it is added there. Device-local UI state (view, active project, filters, timer, dismissed tips) is deliberately not synced. Row hashes are taken over `toWire` output, so a codec's `toWire` must only emit an optional new field (like `Todo.status`) when it is set: an always-present key (even `null`) changes every existing row's hash, re-stamps them all as edited and re-pushes them, which can clobber unpulled edits from other devices.

The admin panel is for the one account whose email equals the backend's `ADMIN_EMAIL` (no role column; `BearerTokenFilter` grants `ROLE_ADMIN`, `SecurityConfig` guards `/api/admin/**`, see `backend/README.md`). `AccountService.isAdmin` asks `/api/admin/me`; the menu entry and the `admin` view (`AdminViewComponent` + `AdminUserModalComponent`, state in `AdminService`) exist only while it is true. The admin API returns account metadata and counts, never task or project content.

## Architecture

- **Entry:** `src/main.ts` → `src/app/app.component.ts` (`AppComponent`, standalone, bootstrapped via `bootstrapApplication`)
- **Framework:** Angular 19 (standalone components, signals) + Angular CLI (esbuild `application` builder) + TypeScript + `@ngx-translate/core`
- **Change detection:** zoneless (`provideExperimentalZonelessChangeDetection`, no zone.js polyfill). Every component is `ChangeDetectionStrategy.OnPush` and every piece of state is a signal — new components must follow both, or they will not update.
- **Lazy loading:** `app.component.html` wraps each view in `@defer (on immediate)`, so each is its own chunk. Adding a view means adding a `@defer` branch, not just an import. Three more surfaces are deferred the same way: the Matrix tab of `projects-view` (the `eisenhower-view`), and the global Plan-my-day modal (`planning-lab-modal`, wrapping the `daily-backlog-view` wizard), which `AppComponent` renders outside the view chain whenever `ViewService.planningOpen` is true, and the Configuration modal, rendered the same way from `ViewService.configOpen`. The views are `pomodoro`, `projects` (labelled "Tasks and projects"; Projects | Matrix tabs, with the former General backlog folded into `projects-panel` behind its opt-in `withBacklog` input), `project` and `admin`. `project` is the detail view of one project (`project-detail-view`, reached by the opt-in `manageable` Manage project button of `project-tree-item`): `ViewService.activeProjectId` and `projectPresentation` (both persisted) pick what it shows (`overview`, `kanban`, `list`, `matrix`, `roadmap`, `calendar`, `flow`; an unknown stored value falls back to `kanban`, validated in `view.service.ts`), it falls back to `projects` when the project no longer exists, and each presentation is deferred inside it, so each is its own chunk: `project-overview` (stat tiles, per-milestone progress, hand-written SVG burn-up from `lib/burnup.ts`, priority and age breakdowns), `kanban-board` (cards: `kanban-card`), `project-task-list` (sortable, inline-editable table with bulk actions) and `eisenhower-view` with its `projectId` input set (the Matrix, limited to the project), `project-roadmap` (milestone bars from start to due, filled by progress, expandable to dated tasks, dragging a bar shifts its dates by whole days; one computed lays everything out in pixels, `ZOOM` weeks 28 / months 8 / quarters 3 px per day) `project-calendar` (month/week grid by `dueDate`; native drag & drop onto a day plus a ⋯ date field on each chip for keyboard and touch; an Unscheduled panel for open tasks without a due date) and `project-flow` (see **Flow diagram** below). The Roadmap and the Overview's milestone rows share `milestone-dates-modal` (name, start, due; swaps a backwards range). `ViewService.showDoneTasks` (device-local, default false) hides completed tasks in Kanban, List and Calendar alike (the Done column keeps its drop target and a "N done · Show" placeholder), and `ViewService.kanbanMilestoneFilter` is the board's per-project milestone filter, shared so the Overview can open the board already filtered (`openKanbanForMilestone`). A new presentation is a `PRESENTATIONS` entry plus a `@case` in `project-detail-view`; legacy stored `planning-lab`/`eisenhower` values are migrated in `view.service.ts`.
- **Services** (`src/services/`, `@Injectable({ providedIn: 'root' })`, one per former Pinia store): `settings.service.ts` (theme, language, durations), `todos.service.ts` (todo CRUD, filters, import/export), `clock.service.ts` (timer state, bell sounds), `view.service.ts` (active view, `projectsTab`, `planningOpen`, `focusQuadrant`, clock-settings panel and `configOpen`/`configSection` state; device-local, not synced), `projects.service.ts` (project tree), `multitask.service.ts` (task drawer/multitask), `flow.service.ts` (Flow data, see below). All persisted state uses `localStorageSignal` (`src/core/local-storage-signal.ts`) writing to `productivist.*` localStorage keys; it skips writes that would not change the stored value and coalesces bursts into one write per key per microtask.
- **Components:** `src/app/components/<kebab-name>/<kebab-name>.component.{ts,html,css}`, one directory per component, standalone, leaf-first dependency order.
- **i18n:** `@ngx-translate/core`. English is registered synchronously in `AppComponent`'s constructor via `setTranslation()`; every other locale is dynamically imported the first time it is selected. Messages in `src/i18n/locales/{en,es}.json`. Default/fallback: `en`. Use the `translate` pipe in templates (`{{ 'key' | translate }}`) or inject `TranslateService` and call `.instant(key)` for non-template usage (e.g. inside `window.confirm`).
- **Task status:** `Todo.status` (`'todo' | 'inProgress' | 'review'`, absent = todo) is the Kanban workflow column; `done` stays the single source of truth for completion and the board's Done column is derived (`columnOf` in `lib/kanban.ts`). Toggling `done` elsewhere leaves `status` alone; `TodosService.moveOnBoard` is the one place that changes both together.
- **Dates:** `Todo` and `Milestone` have optional `startDate`/`dueDate`, plain local-calendar `'YYYY-MM-DD'` strings (never `Date` or epoch ms: a due date is a day, not an instant). Parse with `parseIso` in `lib/dates.ts` (local midnight), never `new Date('2026-10-10')` (UTC); format with `Intl.DateTimeFormat(settings.language(), …)` in a `computed`, not `DatePipe` (no Angular locale data is registered). `lib/dates.ts` also has `todayIso`, `toIso`, `isIsoDate`, `addDays`, `diffDays`, `startOfWeek` (Monday), `startOfMonth`, `monthGrid`, `dueState`, `orderedDates` (swaps start > due) and `sanitizeDates`. The sync codecs emit each date only when set (like `status`) and the backend stores them as `TEXT` with a `YYYY-MM-DD` CHECK (`V4__dates.sql`). Export files are `version: 3` (2 and 3 import the same way); import runs `sanitizeDates` over todos and milestones so a hand-edited file cannot wedge sync.
- **Flow data** (the Flow view's model; the diagram is described under **Flow diagram**): a project's `Objective`s (`src/types/flow.ts`: `horizon` short/medium/long, `status` active/achieved/dropped, optional `description` and `targetDate` as 'YYYY-MM-DD', `order`) are the outcomes its work is for. They are not tasks and not the daily planner's free-text "today's objectives". A `FlowLink` is a row `{ fromKind: 'task' | 'milestone' | 'objective', fromId, toObjectiveId, projectId }` meaning "from contributes to the objective", so `Todo`/`Milestone` and their sync hashes are untouched. A `FlowLayout` is one row per project (`id` = project id) with `positions` (`${kind}:${id}` → `{x, y}`, kind `objective`, `milestone` or `nomilestone` with the project id) and `collapsed` card keys; it is its own row so dragging a node never re-stamps a task or milestone. `FlowService` (root, no dependencies, in the initial bundle, so no layout maths here) owns the three `localStorageSignal`s `productivist.objectives`, `productivist.flowLinks`, `productivist.flowLayouts`: objective CRUD (`addObjective`, `updateObjective`, `removeObjective`; a horizon change drops the objective links that stop pointing to a longer horizon), `link(from, toObjectiveId)` (returns null or the `LinkRefusal`), `unlink`, `setPosition`/`setPositions`/`clearPositions`/`setCollapsed` (call once on pointer-up), `objectivesByProject`/`linksByProject`/`layoutsByProject` maps, `exportFlow`/`importFlow`/`reset` and `sweep`. `lib/flow-rules.ts` is the pure rulebook (task/milestone → any objective of the same project; objective → only a strictly longer horizon, which rules out cycles; no duplicates) with `validateLink`, `validTargets` (for highlighting while dragging) and `isLinkCoherent`; the store enforces it, the diagram reuses it. Cascades: `ProjectsService.removeProject` → `FlowService.removeForProject`, `removeMilestone` and `TodosService.removeTodo`/`removeMany` → `removeLinksFrom`. `ProjectsService.sweepFlow()` (startup, after every sync pull, after an import) drops anything pointing at a vanished project, milestone or task (or a task that moved to another project); it lives in `ProjectsService` because `FlowService` must not inject the stores that call it. Sync codecs `objectiveCodec`, `flowLinkCodec`, `flowLayoutCodec` follow the same rule as the others (optional `description`/`targetDate` only when set; layout keys are sorted before hashing). Export files are now `version: 4` and add `objectives`, `flowLinks`, `flowLayouts`; import accepts 2 to 4 (missing arrays are empty), skips malformed rows, drops invalid `targetDate`s and links that join nothing, and Reset clears the store. Backend: `V5__flow.sql` creates `objectives`, `flow_links` and `flow_layouts` (layout positions/collapsed are JSONB, checked for shape and size in `SyncService.java`); the new push/pull lists are optional so older clients keep working.
- **Flow diagram** (the `flow` presentation): `project-flow` is the presentation root (toolbar: VIEW segmented Diagram | Outline, Horizon and Status `.filter-chip`s where an empty set means "All", the shared `ViewService.showDoneTasks` switch, ghost buttons + Objective / + Milestone and, in Diagram mode only, Tidy up / Fit and zoom − / + with the % readout; it also owns the editors: `objective-modal`, `milestone-dates-modal`, `task-detail-modal`). `flow-canvas` is the diagram: a viewport (`touch-action: none`, `overflow: hidden`) holding one world `div` moved with a single `translate() scale()`, the four lane bands (Work | Short | Medium | Long), an SVG layer of links and the cards (`flow-milestone-node` for milestones and the dashed "No milestone" card whose header has no port, `flow-objective-node`). The cards are presentational; the canvas runs every gesture from `data-key` / `data-drag` / `data-port` attributes with one set of handlers on the viewport and a non-reactive `gesture` field: drag empty space or wheel to pan, Ctrl+wheel to zoom around the cursor, drag a card header to move (the live position is a local `drag` signal, committed once on pointer-up with `FlowService.setPosition`), dropping an objective in another horizon lane changes its horizon (asks first if that would drop objective links), drag from a ● port to an objective to link (`validTargets` highlights while dragging; a refused drop flashes the card and shows `flow.refusals.*`), click a link then ✕ or Delete to unlink, drag a task row's ⠿ grip onto another card to change its milestone, `+ Add task` per card, collapse per card, double-click a card or press Enter to edit it, double-click an empty horizon lane to create an objective there; Escape clears the selection (and only then swallows the key, so a bare Escape still leaves the project). Keyboard and touch: the selected node (card, or task row by mouse/touch) shows a ⋯ button, and `L` / the Menu key / Shift+F10 open the same `flow-link-menu` (a small dialog of buttons: the objectives it may link to via `validTargets`, and its existing links, each removable; Escape closes it and is swallowed so it does not leave the project; focus goes back to the node), Alt + arrows move the selected card by 8 world px (Shift: 32; an objective's Left/Right jump to the neighbouring horizon lane, which asks the same confirm as a drag when links would break) through `commitMove`, and Alt + Left is stopped there so it does not also mean "back". Touch: one finger pans, two fingers pinch-zoom around their midpoint (`touches`/`pinch` fields; a second finger cancels any one-finger gesture). A port's grab area (`.flow-port::before`) is as tall as its row and about 28 screen px wide at any zoom (`--flow-k`, the canvas zoom, is set on the world `div`), and `portNear` also treats a press within 14 screen px of a port as a press on it. A project with no stored viewport is fitted on first render without saving it (`fit(true)`), and again whenever the canvas resizes while narrower than 480 px, until the user pans or zooms (`pendingFit`). Tidy up asks `window.confirm` when any position is stored (there is no undo). After a task is added or a card expanded, `settleBelow` (using `pushDownOverlaps` in `lib/flow-layout.ts`) pushes down only the hand-placed cards the grown card now covers; unplaced cards restack by themselves. Outline mode (`flow-outline`, the default below 700 px wide, not remembered) is the same graph as an indented list built with `buildFlowGraph`/`chainOf`: objectives from the longest horizon down (roots = shown objectives that feed no other shown one), each with its sub-objectives, linked milestones (with their tasks, collapsed by default) and linked tasks, then a section for work that serves no objective yet; every title and every ⋯ link menu is a real button, so tasks are fully keyboard-accessible there, and it shares the filters and editors of `project-flow`. Elsewhere: the Overview's *Objectives* card (per horizon, progress from `buildFlowGraph`, "Open in Flow") and the read-only 🎯 chip (`objective-chip`, fed by `objectivesServing` in `lib/flow-graph.ts`, one computed map per Kanban board / List) on Kanban cards and List rows. Selecting a node dims everything outside its chain (`chainOf`: what it feeds, and for an objective what feeds it). Pan and zoom are per project in device-local `productivist.flowViewport` (not synced; a first visit fits the diagram). Above ~150 nodes only those near the viewport are rendered. Three pure libs, imported only by the Flow components: `lib/flow-graph.ts` (`buildFlowGraph`: cards, deduplicated progress roll-up, `chainOf`; node keys are `objective:<id>`, `milestone:<id>`, `nomilestone:<projectId>`, `task:<id>`), `lib/flow-layout.ts` (`layoutFlow`: lane columns are fixed, stored y wins, the rest is stacked into free space, objectives near the average height of what feeds them) and `lib/flow-geometry.ts` (fixed card metrics, so port positions are computed from a card's position and never measured; Bézier paths, fit and zoom maths). The card components bind the same metrics as inline sizes (`HEADER_HEIGHT`, `ROW_HEIGHT`, …), so change a size in the geometry file, not in the CSS. The horizon hues are `--color-horizon-short/medium/long` in `style.css`, derived from existing tokens so every theme gets its own. Only `project-detail-view` may import `project-flow`; nothing else may import the Flow components (`flow-canvas`, the node cards, `flow-outline`, `flow-link-menu`, `objective-modal`) or `flow-layout`/`flow-geometry`. `lib/flow-graph.ts` is also used by the lazy Overview, Kanban and List (never by the initial bundle).
- **Lazy-chunk check:** `scripts/check-lazy-chunks.mjs` reads `dist/productivist/stats.json` (`ng build --stats-json`; `npm run check:lazy` builds and runs it), follows static imports from `main.ts` to find the initial chunks and fails if any presentation component (`project-overview`, `kanban-board`, `project-task-list`, `eisenhower-view`, `project-roadmap`, `project-calendar`, `project-flow`) is in one, if the Flow-only files (the Flow components, `flow-layout`, `flow-geometry`) appear in a chunk without `project-flow`, or if `flow-graph`/`objective-chip` (shared by several lazy chunks) reach an initial chunk. Run it after adding a presentation (and add the new one to its list); no `prefetch` on the `@defer` blocks, which would load every tab's code up front.
- **Types:** `src/types/todo.ts`, `multitask.ts`, `eisenhower.ts`, `project.ts` (framework-agnostic, unchanged from the Vue version)

## TS constraints (from `tsconfig.json`)

- `strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `noImplicitReturns`, `noPropertyAccessFromIndexSignature` — all enabled
- No `erasableSyntaxOnly` (requires TS 5.8+; this repo pins `~5.7.2` for Angular 19 compatibility) — avoid constructor parameter properties anyway (use `inject()` instead of constructor DI) to keep the option easy to re-enable later
- Angular strict template checking is on (`strictTemplates`, `strictInjectionParameters`, `strictInputAccessModifiers`)

## Shared building blocks

Reach for these before writing new markup — each exists because the same thing had been copy-pasted across many components:

- `task-badges` — a task's importance/urgency chips, `[showTags]` to append its tags
- `inline-task-editor` — the compact edit-in-place form (title, priorities, tags)
- `priority-select` — the low/medium/high dropdown
- `project-milestone-picker` — the project + milestone selects with their inline "new project"/"new milestone" forms
- `.badge*`, `.modal-overlay` and `.modal-panel` in `src/style.css` — modals compose the last two and set only their deltas through `--modal-max-width`, `--modal-max-height`, `--modal-radius`, `--modal-padding`, `--modal-gap` and `--modal-z`
- `lib/eisenhower.ts` — the one `QUADRANTS` table (keys, css keys, label keys and the importance/urgency a quadrant implies), plus `classify`, `comparePriority`, `countByQuadrant`, `compareByUrgency`
- `lib/kanban.ts` — the one `BOARD_COLUMNS` table, `columnOf` (todo → board column) and `reorderSlice` (re-orders one column slice reusing its own `order` values, so other todos keep theirs)
- Toolbar controls in `src/style.css`, used by every project presentation so a mode, a filter, a toggle and an action look different: `.segmented` + `.segmented__option` (pick a mode; on = `aria-pressed="true"`, prefixed by a `.control-label`), `.filter-chip` (narrow what shows; on = `aria-pressed="true"`), `.switch` (a `<button role="switch" aria-checked>` with a `.switch__track` span, then the label) and `.button-ghost` (do something)
- `objective-chip` — the read-only 🎯 chip naming the objectives a task serves (`[titles]`); `lib/flow-graph.ts` `objectivesServing` builds the task → titles map
- `flow-link-menu` — the ⋯ dialog that links a task, milestone or objective to objectives (or removes a link); used by the Outline rows and the diagram's selected node
- `lib/dates.ts` and `lib/burnup.ts` — see Dates above (the Roadmap/Calendar-only `endOfMonth`, `isoWeek` and `capitalizeFirst` live in `lib/calendar-dates.ts`, so they stay out of the initial bundle)
- `milestone-dates-modal` — the one editor for a milestone's name and start/due dates; open it from anywhere with an `@if` and the milestone
- `TodosService.updateMany`/`removeMany` — one write for a bulk change; `updateMany({ done })` stamps or clears `completedAt` like `toggleDone`
- `ClockService` — owns `formattedTime`, `maxDurationSeconds` and the `canDecrease/IncreaseDuration` guards, not the views

`task-badges` and `priority-select` are `:host { display: contents }` so their elements stay direct children of the caller's flex container.

## Performance constraints

- Never call a method that builds an array or a Map from a template binding; expose a `computed` (often a `Map` keyed by id) and look it up. See `tasksByMilestone` in `project-tree-item` or `boxes` in `box-clock`.
- The production `initial` budget warns at 350 kB and fails at 450 kB. Adding an eager import to `AppComponent` pulls a whole view back into the initial bundle.

## Design tokens

CSS custom properties in `src/style.css` (unchanged from the Vue version). Four themes: light (`:root`, default), dark (`[data-theme='dark']`, Dracula), japanese (`[data-theme='japanese']`), nordic (`[data-theme='nordic']`). Toggle via `data-theme` attribute on `<html>`, set by an `effect()` in `AppComponent`.

## Conventions

- Services expose state as `signal`/`computed`, not plain properties — always call as a function in templates/TS (`todos.filteredTodos()`, not `todos.filteredTodos`)
- All state mutations are immutable (`.set()`/`.update()` with spread/map, never mutate objects inside a signal's array in place) so change detection picks them up
- Use `inject()` for dependency injection, not constructor parameter properties
- Components use kebab-case class names with `__` modifier syntax (BEM-like): e.g., `main-view__clock`
- Todo `order` field controls display ordering; `reorderTodoBefore` recomputes order values for the affected slice
- Angular's new control-flow syntax (`@if`/`@for`/`@else if`) is used throughout instead of `*ngIf`/`*ngFor`
